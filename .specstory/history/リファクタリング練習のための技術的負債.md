- 静的メソッドの多用

1. **段階的な改善**
- 単一責任の原則に基づく分割

2. **アーキテクチャの改善**

3. **テストの導入**
- 単体テストの追加
- インテグレーションテストの作成
- モック/スタブの活用方法

このアプローチは、実際の現場でよく遭遇する状況に近く、実践的な学習になると思います。段階的なリファクタリングを通じて、コードの品質改善の過程を体験できる良い機会になるでしょう。

ご提案として、最初は意図的に技術的負債を入れつつも、完全に破綻した設計にはせず、段階的なリファクタリングが可能な程度の「適度な負債」を入れることをお勧めします。これにより、リファクタリングの過程で得られる学びがより実践的なものになると考えます。

_**Assistant**_

はい、テスト困難な構造を作り出すための具体的な提案をさせていただきます：

1. **直接DBアクセスを行うロジック**
- TodoControllerで直接クエリビルダーを使用
- EloquentモデルをスキップしてDB::tableを多用
- トランザクション処理をコントローラーに直書き
- RAWクエリの使用

2. **時間に依存する処理**
- `Carbon::now()`を直接コード内で使用
- タスクの期限切れチェックを現在時刻との直接比較で実装
- スケジュールされたタスクの処理で`sleep()`を使用
- キャッシュの有効期限を固定値でハードコーディング

3. **外部APIに直接依存する処理**
- 天気APIを直接TodoControllerから呼び出し
- 通知サービス（Slack等）への直接HTTP請求
- 外部の決済APIを直接コントローラーから実行
- メール送信処理をコントローラーに直書き

4. **静的メソッドの多用**
- ユーティリティクラスを作成して全てのメソッドを静的に
- `TodoHelper::createTask()`のような静的ヘルパーメソッド
- `Config::get()`の直接呼び出し
- `Auth::user()`の多用

具体的な実装例（実際には書かないですが）のイメージ：

```php
class TodoController
{
    public function index()
    {
        // 直接DBアクセス
        $tasks = DB::table('todos')
            ->where('user_id', Auth::id())
            ->where('due_date', '>', Carbon::now())
            ->get();

        // 外部API直接呼び出し
        $weather = file_get_contents('https://api.weather.com/tokyo');

        // 時間依存の処理
        foreach ($tasks as $task) {
            if (Carbon::now()->diffInDays($task->due_date) < 3) {
                Mail::raw('期限が近づいています', function($message) {
                    $message->to(Auth::user()->email);
                });
            }
        }

        // 静的メソッド多用
        TodoHelper::markOverdueTasks();
        NotificationHelper::sendSlackAlert();
        CacheHelper::storeTaskList($tasks);
    }
}
```

このような実装にすることで：
- ユニットテストが困難になる
- モックやスタブの作成が複雑化
- 時間依存の処理のテストが不安定に
- 外部サービスへの依存でテストが遅くなる
- テスト環境のセットアップが煩雑に

これらの問題は後のリファクタリング練習の良い教材となるでしょう。
